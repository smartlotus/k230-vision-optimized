# 失败处理 Playbook

适用场景：流水线某环节失败、链停在半成品状态、或你（Agent）接手一个"上轮跑挂了"的项目。按顺序执行，不要跳步。

## 第 0 步：冻结现场

1. **不要删除任何东西**——半截 CSV、旧日志、FAILED 标记、lock 文件都是证据；
2. 确认没有进程还在写这些文件（查进程列表）；有活跃训练进程则它神圣不可杀，只观察；
3. 读权威状态 `pipeline_state.json`：哪条腿什么状态、attempts 几次、最近失败原因。

常见错误：一上来就重跑。没有根因的重跑 = 掷骰子，且会覆盖/污染现场。

## 第 1 步：定位与归因

1. 读失败腿的 run 目录：`manifest.json`（输入是什么、代码什么版本）+ 日志尾部 + gate_report（如果有）；
2. 区分三类错误，处理方式完全不同：
   - **集成缺口**（代码从没一起跑过）→ 走纳米预演补课，修代码；
   - **瞬时错误**（OOM / 内存 / 网络 / 驱动）→ 记录环境状态，L1 降级重试（批减半、分块、清理后重启）；
   - **配置/数据错误**（路径、阈值、格式）→ 修配置，**不重试**；
3. 找到根因后再继续。按项目既有时间与重试预算推进；持续没有新证据时重新评估诊断路径。只有真实权限/信息缺口或预算耗尽才升级，不因通用 30 分钟计时器强制交接。

## 第 2 步：故障交接包（L2 升级）

### 共享设备和图像链路的分段证据

连接串口、相机或媒体管线前确认唯一控制端；子 Agent 的并行范围可设为只读代码、证据与文档。出现并非本会话启动的脚本或结果时，先核对所有权，不归入自己的运行，也不直接打断。项目已有安装器或恢复规程时，先验证并复用现有入口，避免手工重建一条缺少校验的路径。

传输提交、目标字节完整、脚本执行、输出质量和任务验收分别取证。大工件不要经可能截断的工具文本回显传递；使用有界分片，目标关闭重开后核对完整大小与哈希。工具 success 不替代目标校验。

图像异常先比较合成图案、相机原始帧、转换后文件和主机显示；同帧保存阶段文件与哈希，区分采集、格式转换和传输。预览 available 可能只是缓存，应核对新帧序号、年龄和当前运行身份。结合实际固件对象及精确版本源码验证 API，不把最新文档或 stub 当运行支持证明；运行完成也不等于输出质量通过。

无论由人还是 Agent 接管，都先产出这份包（写入 `.agents/incidents/<日期-主题>.md`，模板见事故复盘模板）：

```markdown
# 故障交接包：<环节> 于 <时间> 失败
- 现象：一句可复述的话（错误类型 + 退出码/错误消息原文）
- 链状态：哪些腿 PASS（run_id）/ 哪条失败 / 哪些被波及未跑
- 根因：<已定位则写，未定位写"待查 + 已排除项">
- 证据：日志绝对路径（行号）、相关文件路径、截图/指标
- 修复建议：<如果有>
- 精确重入命令：<修复后从哪条命令继续，哪些腿会自动跳过>
- 已尝试：attempts 次数与每次失败差异
```

标准：接手的人**不需要读任何其他文档**就能行动。做到这一点的检查方法：把包发给一个没有上下文的 Agent 问"下一步做什么"，答案正确即合格。

## 第 3 步：修复 + 沉淀

1. 修复代码/配置（改前确认 claim、改后写测试）；
2. **F 条目**（见 pipeline-principles.md 准则 7）：问题→方法→旧代码复现证明→测试验证；
3. **加防御**：问"什么 gate 检查能让这个错误在 3 分钟内被抓住而不是 3 小时？"——把答案实现进 gate/编排器；
4. 若修复涉及任何环节脚本 → 触发纳米预演（准则 3），全链绿了才允许重入长跑。

## 第 4 步：幂等重入

1. **不做全链重跑**：已 PASS 的腿凭 gate_report 里的 run_id 直接复用；
2. 失败腿新建 run 目录重跑（准则 1：绝不写进旧 run 目录）；
3. **脏标记传播**：若 A 重跑了，B/C/D 即使之前 PASS 也要标 dirty（它们的输入已不是验收票指认的那份），按需重跑；
4. 重入用权威状态驱动：编排器读 `pipeline_state.json` 决定跳谁跑谁，不要靠人肉记住"这次跳过 A"。

## 何时叫醒人（升级条件）

满足任一条即停下并生成故障交接包，不再自动处理：

- 同一腿重试预算耗尽（默认 3 次，配置类错误 0 次）；
- 需要超出当前授权的动作（如杀他人进程、删除他人文件）；共享配置修改按项目授权判断，不默认禁止任务内常规修复；
- 磁盘/RAM 低于安全水位且降级路径已用尽；
- 发现可疑迹象：产物被未知来源修改、两个 owner 并存、状态文件与磁盘事实矛盾——这可能是另一个 Agent 并行操作，联系而不是覆盖。

## 复盘收尾

事故处理完，把 `.agents/incidents/<日期-主题>.md` 补全为完整复盘（模板），并在项目指定交接记录与 DECISIONS.md 留痕；若 STATE.md 是生成视图，不手改。检查：这次事故暴露的缺口，是否对应七条准则中的某一条没有被遵守？如果是，那是流程问题，不是运气问题。
